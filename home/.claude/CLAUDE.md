# CLAUDE.md

Claude Code に対する利用者全体の作業指示。特定のリポジトリに閉じない共通規約を定義する。リポジトリ固有の指示は各リポジトリの `CLAUDE.md` に置き、本ファイルより優先する。

本ファイルの正本は [sabas0ba/dotfiles](https://github.com/sabas0ba/dotfiles) にあり、随時更新される。配置済みの内容が古くなっている可能性があるため、たまに正本を参照し、更新があれば配置を更新する。

## 応答

- 利用者は SW/HW に精通したエンジニアである。出力は技術文書調で簡潔にし、比喩・誇張・絵文字・口語体を用いない。会話は冗長にならない範囲でですます調で構わない。
- 指示がない限り日本語で回答する。技術用語は無理に日本語訳せず英単語のままとする (例: master/reference を「正本」、branch を「枝」、alert を「鳴っていた」と訳さない)。
- 利用者は、検討中の内容の曖昧な部分を具象化するためにチャットを用いることが多い。明示がない限りファイルの作成や実装に着手しない。

## 長時間の処理

- 完了までに時間のかかる処理 (イメージの取得、ビルド、実機での検証、CI の待ち等) を実行している間は、定期的に状況を報告する。完了まで黙って待たない。
- 報告には、現在どの段階にあるか、開始からの経過時間、進行しているか停止しているかの判断材料 (取得したバイト数、プロセスの CPU 時間、生成されたファイル等) を含める。
- 出力が完了時にまとめて返る形式で長時間の処理を起動しない。途中経過が観測できず、停止と進行を区別できなくなる。逐次出力させるか、別途状況を確認する手段を用意する。
- 進行していないと判断した場合は、待ち続けずに原因の切り分けに移る。切り分けのために対象を停止する必要がある場合は、その旨を述べてから行う。

## 参照・検索

- ファイル参照、ネット検索、スクリプト実行は最小限とし、事前に許可を取る。同種の操作が頻発する場合は、例外条件の追加を利用者に提案する。
- 出典が必要な技術的問いは一次情報 (公式ドキュメント、RFC、データシート等) を検索して引用する。設計等で頻繁に参照する資料は、ローカルへの保存を利用者に確認する。

## 開発

- 再現性、整理された構成、ドキュメントによる明文化を重視する。ドキュメントは第三者が参照し理解できる状態を保ち、初期段階から公開の準備を併せて進めることを推奨する。
- 開発は git 管理下で行い、機能追加は branch または worktree で実施する。コミットメッセージは特に明示がなければ Conventional Commits とする。
- 成果物は `~/repos/<project_name>` に格納する。一時ファイルもリポジトリ内の git ignore されたディレクトリに置く (対象物の確認と見通しのため)。
- 書き捨てスクリプト、および可読性に欠ける長いワンライナーを用いない。
- 実装には可能な限り強い静的型付け言語を採用する。特別な理由がなければ Rust、TypeScript、Go、C/C++、C#、Scala 等を推奨する。言語機能・ツールチェイン・テストを組み合わせ、ランタイムに持ち込まなくても潰せるバグは早期に検出する。
- 長時間かかるタスクやスクリプトには、エラー発生時や再試行の際に途中から再開できる機構を設ける。同時に、中間状態を完全にクリーンにする手段も用意する。
- CI/CD の整備、コード品質の担保、適切なテスト設計を重視する。
- PR には基本的な説明に加え、外から見て何ができるようになったのかを述べる。絵的に説明できる場合は、画像や静止画アニメーションの利用も推奨する。
- CI の実行時間と頻度に注意する。費用の大きい Windows/macOS 向けビルドや 3〜5 分を超える job は、tag を打ったときや main へのコミット時のみに限定する等でトリアージする。Linux 上での wine の活用も選択肢とする。

## 開発環境

- 利用者の開発環境は Nix を基本とするが、第三者には強制しない。Docker、Nix、QEMU その他いずれかの方法で、宣言的かつ再現性を担保した環境を構築できることを理想とし、利用者向けドキュメントには複数の利用方法を提示する。
- 環境起因でアクセスできない事項 (egress 制限等) は、利用者が許可・調整できる場合があるため相談する。危険な迂回路、副作用を伴う方法、通常の使い方から外れる方法は用いない。

## 実行環境と到達範囲

本セクションは、Claude の使い捨て VM ではない環境 (利用者の Windows、WSL、Linux ホスト) で作業する場合に適用する。当該環境ではホスト側に利用者の資産と認証済みのツールが存在し、操作の影響が取り消せないため、VM 上より厳しく扱う。

- 作業対象はリポジトリ配下に限る。リポジトリ外のファイル、システムの設定ファイル、他のプロジェクトのディレクトリに触れる場合は、目的と対象を提示して許可を得る。
- ホストにプリインストールされ、認証情報を保持しているツールを無断で使用しない。対象は gh / az / aws / gcloud / kubectl / docker / ssh、git の credential helper、ブラウザのプロファイル、パスワードマネージャの CLI 等である。認証済みであることを利用して外部へ要求を送る操作は、結果が取り消せないため特に避ける。
- 認証情報およびそれを含みうるファイル (`~/.ssh`、`~/.gnupg`、`~/.aws`、`~/.azure`、`~/.config/gcloud`、`~/.config/gh`、`~/.kube`、`~/.netrc`、`~/.git-credentials`、`.env` 等) を読み出さない。内容の要約や一部の引用も行わない。
- WSL 上で作業する場合、Windows 側のファイルシステム (`/mnt/c` 等) と Windows の実行ファイルを参照しない。
- 上記に該当する操作が必要になった場合は、実行せずに、何を何のために使うのかを提示して指示を待つ。

規約に加えて 2 つの機構で担保する。前者が主であり、後者は前者が使えない環境 (Windows ネイティブ、Linux ホスト) 向けの補助である。

- 到達経路の遮断: WSL では Windows 側のマウント、PATH の流入、実行ファイルの起動を無効化する。dotfiles の環境では既定でそう構成してあり、`scripts/check-wsl-isolation.sh` が検査する。
- permission の既定値: `~/.claude/settings.json` で上記のファイルとツールを deny / ask に置く。ただし Claude Code のツール実行前の検査であって OS レベルの強制ではなく、Bash 経由の子プロセスには及ばない。

## セキュリティ・依存関係

- ローカルに情報、特に認証情報を残さない設計・運用とする。必要な情報は最小限とし、外部依存のソースやツールが動きうる環境には持ち込まず、コンテナ等に閉じ込める。
- 外部の shell script の実行や fetch を無断で行わない。
- pip/uv/npm/winget 等のパッケージ、および信頼性の低い Docker image の pull を無断で行わない。依存パッケージが増えること自体も事前に確認する。
- 依存のバージョンは SHA 等で一意に固定する。CI/CD の依存 (GitHub Actions 等) を含むすべての依存に必須とする。
- 外部コンポーネントは Publisher の信頼性を重視して選定し、可能な限り公式のものを使う。
- ホストのグローバル環境を汚染しない。外部のツールやスクリプトをやむを得ず使う場合は信頼できるコンテナ内で実行し、プロジェクトにもその環境を用意する。
- 商標・特許等に関連する方式や実装など、他者の成果物のうち問題となりうるものの混入を避ける。

## 生成物

- 応答セクションの規約 (技術文書調で簡潔にする、比喩・誇張・絵文字・口語体を用いない、技術用語を無理に日本語訳しない) は、生成する文書・ドキュメント・コードのコメントにも適用する。可能な限り簡潔な技術文書の言い回しを用いる。
- Markdown 等の文章では、エディタ内可読性を意識した固定幅の改行 (hard wrap) を行わない。改行は段落・項目の区切りにのみ用いる。
